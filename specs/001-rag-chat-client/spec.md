# Feature Specification: RAG Chat Client

**Feature Branch**: `001-rag-chat-client`  
**Created**: 2025-02-15  
**Status**: Draft  
**Input**: User description: RAG chat client with AI-powered Q&A, document management, chat sharing, and admin document upload. Regular users and admins. Local API for PDF storage and AI responses.

## Clarifications

### Session 2025-02-15

- Q: How does the chat owner share a chat with another user? → A: Invite by identifier — Owner enters another user's username or email to grant access.
- Q: Can a single user query across multiple document groups? → A: Multiple groups — User can select which document group to query; each chat or query can use a different group.
- Q: When the owner deletes a chat, what happens for shared users? → A: Can be removed by creator only — Only the creator can delete; when creator deletes, the chat is removed for everyone.
- Q: When a user clicks a source link, how does the document open? → A: New tab/window — Document opens in a new browser tab or window.
- Q: When users "group" chats, what does that mean? → A: Folders — User creates folders and moves chats into them (e.g., "Project X", "Personal").

## User Scenarios & Testing _(mandatory)_

### User Story 1 - Ask Question and Get Answer with Sources (Priority: P1)

A registered user selects a document group, enters a question in the chat area, and submits it. The system returns an AI-generated answer. Each answer includes citations to source documents. The user can click a source link and is taken directly to the specific page in the document—no scrolling required.

**Why this priority**: Core value proposition; without Q&A with sources, the application has no purpose.

**Independent Test**: User submits a question and receives an answer with clickable source links; clicking a link opens the document at the correct page.

**Acceptance Scenarios**:

1. **Given** user is authenticated and documents exist in a group, **When** user enters a question and submits, **Then** system displays the AI-generated answer with source citations.
2. **Given** an answer with sources is displayed, **When** user clicks a source link, **Then** the document opens in a new tab or window at the exact page indicated in the citation.
3. **Given** user has selected a document group, **When** user submits a question, **Then** the system queries only documents within that group.

---

### User Story 2 - Chat Persistence and History (Priority: P2)

All chats are saved. The user can view a list of past chats and open any chat to see the full message history. Messages include both user questions and system responses with sources.

**Why this priority**: Persistence enables users to return to previous conversations and build on prior context.

**Independent Test**: User creates a chat, leaves, returns later, and sees the chat in the list with all messages intact.

**Acceptance Scenarios**:

1. **Given** user has submitted at least one message, **When** user navigates to chat list, **Then** the chat appears with a generated name.
2. **Given** user selects a chat from the list, **When** the chat opens, **Then** all messages (questions and answers with sources) are displayed in chronological order in the main panel to the right of the sidebar.
3. **Given** user has multiple chats, **When** user views the list, **Then** chats are displayed with names and are identifiable.

---

### User Story 3 - First Message Flow (No Chats Yet) (Priority: P3)

When the user has no chats, a query input area is shown alongside the chat list sidebar. The user enters a question and submits. The system implicitly selects an appropriate knowledge scope (e.g., the first available scope) — the user does not see the scope selector at this moment. Upon submission, the user is redirected to a new chat page. The chat name is generated by the system (provided by the API) and displayed. The system response appears with source links.

**Why this priority**: Enables new users to start using the system immediately without an empty or confusing state.

**Independent Test**: User with zero chats enters a question, submits, and is taken to a new chat with the response and a system-generated chat name.

**Acceptance Scenarios**:

1. **Given** user has no chats, **When** user sees the interface, **Then** a query input area is the primary focus of the screen (see UX-004), visually centered in the main area while the chat sidebar remains pinned to the left edge.
2. **Given** user enters a question and submits, **When** generation starts, **Then** user is redirected to a new chat page.
3. **Given** the API returns a chat name, **When** the response is displayed, **Then** the chat name appears in the chat list and header.
4. **Given** generation is in progress, **When** user waits, **Then** a loading indicator (spinner) is shown.

---

### User Story 4 - Chat Management (Priority: P4)

The user can share chats with other users. The chat creator is the owner; this role cannot be removed. The owner can revoke access for any other user with access. Users can search chats by name and search by message content (entering a query shows which chat contains that message). Chats can be pinned, organized into folders, deleted (creator only), or renamed.

**Why this priority**: Collaboration and organization improve usability for active users.

**Independent Test**: Owner shares a chat, revokes access for one user, and that user no longer sees the chat. User searches by chat name and by message content and finds the correct chats.

**Acceptance Scenarios**:

1. **Given** user owns a chat, **When** user enters another user's username or email to share, **Then** the recipient gains access and can view and interact with the chat.
2. **Given** user owns a chat shared with others, **When** user revokes access for a specific user, **Then** that user loses access and no longer sees the chat.
3. **Given** user is the chat creator, **When** viewing permissions, **Then** the owner role is always present and cannot be removed.
4. **Given** user has multiple chats, **When** user searches by chat name, **Then** matching chats are displayed.
5. **Given** user enters a search query, **When** searching by message content, **Then** chats containing that message are displayed.
6. **Given** user has chats, **When** user pins a chat, **Then** it appears in a pinned section or is visually distinguished (see UX-005).
7. **Given** user has chats, **When** user creates folders and moves chats into them, **Then** chats are organized into user-defined folders.
8. **Given** user is the chat creator, **When** user deletes the chat, **Then** the chat is removed for the owner and all shared users; shared users cannot delete.
9. **Given** user owns a chat, **When** user renames it, **Then** the new name is displayed and persisted.

---

### User Story 5 - Document Availability Indicator (Priority: P5)

When no documents exist in the system (or in the selected group), the chat feature is unavailable. The application clearly indicates this state so users understand why they cannot ask questions.

**Why this priority**: Prevents user frustration when the system cannot fulfill requests.

**Independent Test**: With no documents in the system, user sees a clear message that chat is unavailable; after documents are added, chat becomes available.

**Acceptance Scenarios**:

1. **Given** no documents exist in the system, **When** user navigates to chat area, **Then** an explicit message indicates that chat is unavailable and query input is not submit-enabled (see UX-006).
2. **Given** documents exist in at least one group, **When** user selects that group, **Then** chat is available.
3. **Given** a group has no documents, **When** user selects that group, **Then** chat is indicated as unavailable for that group with an explicit message (see UX-006).

---

### User Story 6 - Admin Document Management (Priority: P6)

Admins have all regular user capabilities plus: upload PDF documents, create document groups (knowledge scopes), and bind uploaded documents to a specific scope. Admins can view a list of documents in the system (e.g., first 10 items with pagination controls) with the ability to re-index and delete each document. Upload is initiated from a dedicated button and performed in a modal form. The client validates files before upload: only PDF format, maximum 20MB. Invalid files are rejected by the client and never sent to the server.

**Why this priority**: Admins populate the knowledge base; without documents, users cannot get answers.

**Independent Test**: Admin creates a group, uploads a valid PDF under 20MB, and sees it in the document list. Admin attempts to upload a 25MB file or non-PDF and is blocked before submission.

**Acceptance Scenarios**:

1. **Given** user is an admin, **When** user navigates to document management, **Then** options to create groups and upload documents are available.
2. **Given** admin creates a document group, **When** group is saved, **Then** it appears in the group list and can be selected for document binding.
3. **Given** admin uploads a PDF under 20MB to a group, **When** upload completes, **Then** the document appears in the document list and is bound to that group.
4. **Given** admin selects a file that is not PDF or exceeds 20MB, **When** admin attempts upload, **Then** the system rejects the file, displays feedback to the user (UX-010), and does not submit it.
5. **Given** user is an admin, **When** user views the document list, **Then** at least the first page of documents (e.g., up to 10 items) is displayed with their scope associations, and each document has actions to re-index and delete.
6. **Given** user is a regular user, **When** user views the application, **Then** document upload, document list, and document management actions are not accessible.

---

### User Story 7 - Main Page, Navigation, and UX (Priority: P7)

A main page provides navigation: link to chat (all registered users), link to document management (admins only), and link to knowledge scopes management (admins only). The header contains navigation tabs (Chats, Documents, Knowledge scopes), user-relevant controls, and a language selector. The footer contains standard application information (e.g., copyright, links, version). All page transitions are smooth with no abrupt jumps. Loading states show a spinner. The interface supports Russian and English; the user can change the language. The interface is intuitive for any user (measured by SC-009: first question-answer flow completable in under 2 minutes without external guidance).

**Why this priority**: Ensures coherent navigation and professional, accessible experience.

**Independent Test**: User navigates between main page, chat, and (if admin) document areas; transitions are smooth; loading shows spinners; language can be switched.

**Acceptance Scenarios**:

1. **Given** user is on the main page, **When** user is an admin, **Then** navigation for documents and knowledge scopes is visible.
2. **Given** user is on the main page, **When** user is registered, **Then** navigation for chat is visible.
3. **Given** user navigates between pages, **When** transition occurs, **Then** the transition is smooth with no abrupt visual jumps.
4. **Given** data is loading, **When** user waits, **Then** a spinner or loading indicator is displayed.
5. **Given** user prefers a different language, **When** user changes the interface language, **Then** the interface displays in Russian or English as selected.
6. **Given** the header is displayed, **When** user views it, **Then** it contains navigation tabs (Chats, Documents, Knowledge scopes where applicable) and relevant controls (e.g., user menu, language selector).
7. **Given** the footer is displayed, **When** user views it, **Then** it contains standard application information appropriate for the product.

---

### Edge Cases

- What happens when the user submits a question while the system has no documents? The system indicates that chat is unavailable and does not allow submission (UX-006).
- What happens when a shared user's access is revoked mid-session? The chat disappears from their view on next navigation or refresh; in-session behavior should gracefully handle revocation (e.g., redirect or hide chat).
- What happens when the API fails or times out? The user sees an error message; loading spinner stops; the user can retry (UX-007).
- What happens when the user uploads a file that passes client validation but the server rejects it (e.g., corrupted PDF)? The server returns an error; the client displays the error to the user.
- What happens when the user searches for a message that exists in no chat? The search returns no results or an empty state (UX-009).
- What happens when the chat name from the API is delayed? The chat appears with a placeholder or "New chat" until the name arrives, then updates (UX-008).

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: System MUST allow authenticated users to submit text queries and receive AI-generated answers with source citations.
- **FR-002**: System MUST display source links that open documents at the exact page indicated in the citation; documents open in a new browser tab or window.
- **FR-003**: System MUST persist all chats and messages; users MUST be able to view chat history and all messages in a chat.
- **FR-004**: System MUST support sharing chats with other users; the owner grants access by entering the recipient's username or email; the chat creator is the owner and cannot be demoted.
- **FR-005**: System MUST allow the chat owner to revoke access for any other user with access.
- **FR-006**: System MUST allow users to search chats by name.
- **FR-007**: System MUST allow users to search by message content and display which chat(s) contain the matching message.
- **FR-008**: System MUST allow users to pin chats and organize chats into user-created folders.
- **FR-009**: System MUST allow only the chat creator to delete a chat; when the creator deletes, the chat is removed for all users (owner and shared); shared users cannot delete; rename is permitted for the creator.
- **FR-010**: When the user has no chats, the system MUST display a query input; on submit, redirect to a new chat and display the response with a system-generated chat name from the API.
- **FR-011**: System MUST display source links only to internal documents (files in the system); no external links.
- **FR-012**: When no documents exist in the system (or selected group), the system MUST clearly indicate that chat is unavailable (see UX-006).
- **FR-013**: Admins MUST be able to upload PDF documents, create document groups, and bind documents to groups.
- **FR-014**: Admins MUST be able to view a paginated list of documents (e.g., 10 per page) in the system, including each document's name, scope, and a link suitable for opening the document in a new tab; the list MUST provide actions to re-index and delete a document.
- **FR-015**: The system MUST validate uploads before submission: only PDF format, maximum 20MB; invalid files MUST be rejected and never submitted.
- **FR-016**: System MUST support interface languages: Russian and English; user preference MUST be persistable.
- **FR-017**: Main page and header MUST provide navigation to chat (all registered users), document management (admins), and knowledge scopes management (admins).
- **FR-018**: Header MUST contain navigation tabs and user-relevant controls (see UX-014); footer MUST contain standard application information (see UX-015).
- **FR-019**: All page transitions MUST be smooth (see UX-013); loading states MUST display a spinner.
- **FR-020**: System MUST route all requests (queries, document uploads, document management, scope management) to the existing local API.
- **FR-021**: Admins MUST be able to view a paginated list of knowledge scopes (e.g., 10 per page) and create new scopes inline on the scopes page without using a modal.

### UX Requirements

The following requirements clarify and extend functional requirements for design handoff. Design-time decisions (exact wording, visual tokens) may refine these.

- **UX-001**: Chat area MUST include: a sidebar with chat list pinned to the left edge, a message list (chronological) in the main panel, a query input area, and a document group selector when appropriate. The selector may be hidden when a sensible default scope is auto-selected for the user (e.g., on the very first message flow) but MUST be available in at least one place in the application (e.g., document/knowledge scope management pages) to understand and manage scope choices.
- **UX-002**: Messages MUST be visually distinguishable (user questions vs. system responses); display order MUST be chronological. User messages SHOULD be aligned to the right in one style (e.g., accent background), and system messages SHOULD be aligned to the left in another style with source citations rendered clearly below the answer.
- **UX-003**: Source citations MUST be displayed as clickable links; each link MUST indicate document and page (e.g., "Document X, p. 5"); placement is design-time (inline or list).
- **UX-004**: When the user has no chats, the query input MUST be the primary focus of the screen (centered or dominant; exact layout is design-time) in the main content area to the right of the sidebar.
- **UX-005**: Pinned chats MUST appear in a dedicated pinned section or be visually distinguished (e.g., icon, position) from unpinned chats.
- **UX-006**: When no documents exist (system-wide or in selected group), the system MUST display an explicit message (e.g., "Chat unavailable—no documents in this group") and MUST NOT show a submit-enabled query input.
- **UX-007**: On API failure or timeout, the system MUST display an error message, stop the loading indicator, and provide a retry affordance.
- **UX-008**: When the chat name from the API is delayed, the chat MUST display a placeholder (e.g., "New chat") until the name arrives, then update.
- **UX-009**: Empty states MUST be defined for: zero chats (query input as primary focus, UX-004), zero documents (unavailable message, UX-006), empty search results (e.g., "No matching chats"), and empty folders (design-time).
- **UX-010**: Invalid file upload feedback MUST be shown to the user (e.g., error message near the upload control) before any server request.
- **UX-011**: Interactive elements (links, buttons, inputs) MUST have visible focus states for keyboard navigation; the interface MUST support keyboard-accessible operation.
- **UX-012**: All user-facing strings (including errors, placeholders, empty states) MUST be localizable (Russian and English).
- **UX-013**: Page transitions MUST use animated, non-instant changes (e.g., fade or slide) to avoid jarring visual jumps.
- **UX-014**: Header controls MUST include at least: navigation links (context-appropriate), user menu, and language selector.
- **UX-015**: Footer MUST include at least: copyright and application version; privacy policy and terms of use links may be included (design-time).
- **UX-016**: Long chat names, long message content in list/search results, and long answers with many citations MUST be handled without breaking layout (e.g., truncation, scrolling, wrapping); exact behavior is design-time.

### Key Entities

- **User**: Represents a registered user; has role (regular or admin); can own chats, have access to shared chats, and (if admin) manage documents and groups.
- **Chat**: Represents a conversation; has a name (system-generated or user-renamed), owner (creator), list of messages, and access list (shared users); can be pinned, placed in user-created folders; only the creator can delete (removes for everyone).
- **Message**: A single entry in a chat; either a user question or a system response; responses include source citations.
- **Source / Citation**: Reference to a document and specific page; links open the document in a new tab or window at that page.
- **Document**: A PDF file in the system; belongs to a document group; is the basis for AI answers and source links.
- **Document Group**: A collection of documents; users select which group to query per chat or query; admins create groups and bind documents to them.
- **Chat Folder**: A user-created container for organizing chats; user creates folders (e.g., "Project X", "Personal") and moves chats into them.

## Assumptions

- Authentication and authorization (login, roles) are handled externally; the API uses Bearer JWT; role and identity from claims.  
  For the current client implementation, the JWT is obtained directly from the backend via `POST /api/auth/login` (returns the token as a plain string), stored in an in-memory TokenManager, and then attached to all API calls via the `Authorization: Bearer <token>` header. This flow is intentionally simple so that it can later be replaced with an external OIDC service without touching the rest of the application.
- Users can access multiple scopes (document groups); they select which scope to query per chat or per query; the scope selector is shown in the chat UI when multiple groups exist (UX-001).
- The local API (api-endpoints.md) exposes: submitting queries, receiving responses with chat titles and sources, uploading PDFs, creating/managing groups, and chat CRUD. List documents (GET /documents) is not in the current API.
- Document viewing (opening at a specific page) is supported by the API or a dedicated viewer; the document opens in a new browser tab or window.
- Source citation display format (inline vs. list, exact styling) is a design-time decision; each citation must indicate document and page (UX-003).
- Chat list layout (sidebar, full-page, collapsible), search UI (input placement, name vs. content mode), and folder management UI are design-time decisions.

## API Alignment

The client MUST align with the **Demo RAG API** ([api-endpoints.md](../../api-endpoints.md)). Contract: [contracts/openapi.yaml](./contracts/openapi.yaml).

### API Terminology Mapping

| Spec Term        | API Term                    |
| ---------------- | --------------------------- |
| Document group   | Scope (path: `/api/groups`) |
| documentGroupId  | scopeId                     |
| Chat name        | Chat title                  |
| ownerId (single) | ownerIds (array)            |

### API Endpoints (Summary)

| Capability                          | Endpoint                                           |
| ----------------------------------- | -------------------------------------------------- |
| List/create scopes                  | GET/POST `/api/groups`                             |
| Upload document                     | POST `/api/documents` (scopeId + file)             |
| List/create chats                   | GET/POST `/api/chats`                              |
| Get/delete chat                     | GET/DELETE `/api/chats/{id}`                       |
| Share chat                          | POST `/api/chats/{id}/owners`                      |
| Send message (new or existing chat) | POST `/api/messages` (scopeId+text or chatId+text) |
| Feedback                            | POST/GET `/api/messages/{messageId}/feedback`      |
| Download file                       | GET `/api/files/assets/documents/{fileName}`       |

### Features Not Supported by Current API (Deferred)

The following requirements are **deferred** — no implementation tasks until API support exists:

| Requirement | Status | Reason |
|-------------|--------|--------|
| **FR-005** (revoke access) | Deferred | API has add-owner only; no remove-owner endpoint |
| **FR-006** (search by name) | Client-side only | API returns list with batchSize/lastUsedIndex; client filters by title |
| **FR-007** (search by content) | Deferred | No API support for message-content search |
| **FR-008** (pin, folders) | Deferred | No API fields for pin or folder |
| **FR-009** (rename chat) | Deferred | No PATCH /chats endpoint |
| **FR-014** (list documents) | Deferred | No GET /documents; show local upload state only |

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: Users can submit a question and receive an answer with clickable sources in under 30 seconds for typical queries.
- **SC-002**: Users can open a source and land on the correct page without manual scrolling in 100% of cases when the document is available.
- **SC-003**: Users can find a previous chat from their history within 3 actions (e.g., open list, search, select).
- **SC-004**: Users can share a chat and have the recipient access it within one refresh or navigation.
- **SC-005**: Admins can upload a valid PDF and see it in the document list within 10 seconds of upload completion.
- **SC-006**: Invalid files (non-PDF or over 20MB) are rejected by the client before any server request in 100% of cases.
- **SC-007**: Users can switch interface language and see the change applied across the application immediately.
- **SC-008**: Page transitions complete without visible layout jumps or flicker; loading states are visible within 500ms of a request start.
- **SC-009**: New users can complete their first question-answer flow (from main page to viewing a response) in under 2 minutes without external guidance.
